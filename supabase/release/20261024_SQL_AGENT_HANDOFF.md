## 4. Transaction and error rules

- Enable the runner’s equivalent of **stop on first SQL error**.
- Execute each migration exactly once and separately. The supplied file starts and commits its own transaction.
- After an error, issue only the minimum `ROLLBACK` needed to clear an aborted session, preserve the complete error/statement evidence and stop.
- Never modify a migration, delete a conflicting row, rename an object, weaken a constraint/policy, or rerun blindly to make a failure disappear.
- Treat an unexpected error, warning suggesting skipped security work, checksum mismatch, or an unverified partial prior installation as a stop condition.
- The three test suites deliberately create fictional records inside transactions and end with `rollback`. If a test aborts before its final rollback, issue `ROLLBACK`, verify that no fictional IDs remain, and stop.
- Do not put all seven migrations inside an extra outer transaction: their supplied transaction boundaries are the reviewed release units.
